# Lead Engine repository rules

If starting here and the parent rules are not loaded, read [workspace AGENTS](../AGENTS.md) once. Consult [operations](docs/operations.md) for runtime work and [migration/recovery](docs/migration-and-recovery.md) only for those operations.

- Keep the repository, deployment and D1 private and independent. Do not directly access website D1/R2 or import parent business datasets/artifacts. Reading shared project guidance is allowed. The human-approved minimum customer handoff is the versioned, authenticated and idempotent production exception authorized on 2026-08-26; changing its scope requires owner authorization.
- Leads require human approval before CRM handoff/export or contact. Search/model results are hints; completed companies must pass the shared qualification, evidence, public business-contact and deduplication rules. Discovery has no daily quota; preserve rate limits and visible scoring dimensions.
- No guessed contacts, automatic human approval, email generation/sending or login/paywall bypass. Paid, authenticated, personal-contact or credit-consuming providers need explicit authorization. Missing facts remain missing.
- GitHub is `origin`; `sites` is the deployment remote. Follow parent rules for task-branch commits and safe GitHub synchronization. Never fetch every remote for routine checks.
- Validated application changes pushed to GitHub may be deployed to the existing owner-only Sites project under the standing authorization, without per-release confirmation. Match the exact validated commit, not necessarily main; no implicit main merge. Documentation-only work does not require an application deployment.
- Preserve project ID, access, bindings, secrets and runtime controls. The standing deployment authorization does not allow changing these or starting discovery/outreach. For schema/data changes inspect pending migrations and the needed backup; verify deployment completion and affected behavior. Stop the unsafe external operation and report divergence, access changes, migration risk or failed deployment, while preserving completed local work.
- Use targeted checks while developing; run `npm run check` for code delivery and relevant browser flows for UI changes. Reuse unchanged successful results; documentation changes only need document validation.

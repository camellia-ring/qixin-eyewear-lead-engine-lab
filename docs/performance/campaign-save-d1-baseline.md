# Campaign 保存与 D1 重匹配性能基准

核对日期：2026-08-21（Asia/Shanghai）

## 目标

为 Campaign 策略保存后的全库重匹配建立可重复基线，覆盖生产实现的核心形状：固定批量读取、生产 `campaignMatchesCompany` 匹配器、内存差异规划，以及每批最多 80 条写语句的 D1 批次计数。

运行命令：

```powershell
npm run bench:campaign-save -- --sizes=100,1000,5000 --iterations=12 --warmup=3
```

## 2026-08-21 本地基线

环境：Windows x64，Node v24.14.0；每个样本使用全新内存 SQLite，初始化与造数不计时。场景把 Campaign 从 United States 改为 Canada，使一半历史归属失效、另一半新建归属，并更新全部主 Campaign。

| 公司数 | 计时样本 | 计划写入 | 等价 D1 批次 | p50 | p95 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 12 | 101 | 3 | 1.20 ms | 1.51 ms |
| 1,000 | 12 | 1,001 | 14 | 9.76 ms | 11.58 ms |
| 5,000 | 12 | 5,001 | 64 | 48.16 ms | 50.67 ms |

5,000 家公司的 p50 分解为：Campaign 写入 0.04 ms、批量读取 8.49 ms、差异规划 26.27 ms、本地事务写入 12.35 ms。

## 解释边界

这是 D1 兼容的本地代码路径基线，不是线上延迟声明。本地 SQLite 不包含 Cloudflare D1 的网络、排队、区域和多批次往返延迟；线上耗时预计主要由批次数和网络决定。基准因此同时报告等价 D1 批次数，用来识别写放大。

基准只使用合成公司，不访问或修改生产 D1。后续代码变更应使用相同命令对比 p50/p95、计划写入数和批次数；若要建立线上 SLO，应另行增加无客户数据泄露的服务端计时指标，而不是在生产 Campaign 上反复造数。
